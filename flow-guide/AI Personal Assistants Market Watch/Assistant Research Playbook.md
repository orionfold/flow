# Assistant Research Playbook

## Follow the whole task

Start with a trigger and allowed inputs. Inspect the transformation, persistent output, checking/correction, return and useful next action. Only then ask how the product is acquired, paid for and sustained. A long feature list is useful only if it helps explain this loop.

## Use public sources deliberately

| Public source | Useful signal | Limit to retain |
| --- | --- | --- |
| Official help and release notes | Current contracts, availability and changed behavior | Feature may be a preview, rollout or untested publisher claim. |
| Pricing and allowance pages | Billing units, minimum seats and recurring exposure | Compare matched units; credits are not equivalent task outcomes. |
| Privacy/permission documentation | Access, retention, revocation and approval boundaries | Policy is not a network trace or independent audit. |
| Public status history | Incidents and recovery relevant to the task | Distinguish component incidents from a whole-product failure. |
| App stores and public discussions | User language, unmet tasks and recurring complaints | Anecdotes do not establish prevalence, retention or revenue. |
| Public repositories and developer docs | Visible contracts and extension opportunities | Do not infer private backend design or actual deployed behavior. |

The starting package includes only twelve primary source cards. The other source classes above are useful discovery options, not sources already reviewed. Add them only when a question earns the research.

## Keep five facts separate

**Published:** the identified publisher says it. **Observed:** a captured surface showed it. **Exercised:** you performed the specified action and inspected the result. **Inferred:** your interpretation from named evidence. **Unknown:** the study has not established it. Store availability separately from evidence class and outcome separately from both.

Source capture, citation support and human approval are separate. A checked URL is not a checked claim. A trusted publisher can still have outdated or conflicting documentation. Preserve both versions and the smallest resolving check.

## Watch changes without inventing news

The owner's Watch job starts with three public URLs plus local inputs. A changed digest means the bytes moved. Inspect the material difference before adding a signal. A fixed announcement page cannot discover a newly published article at another URL. Deliberately discover and retain new material as needed.

Start true “changed since last review” with no baseline comparison. On a later cycle record the old source, new source, event date, first-seen date and changed claim. A no-change finding can be a useful result; do not manufacture a weekly story.

## Make a repeated cycle worthwhile

1. Choose one material question from [Research Mandate](Research%20Mandate.md).
2. Inspect the original, retain only the relevant dated evidence and update [Assistant Market Inputs](Assistant%20Market%20Inputs.md).
3. Run the owner's saved Jobs to refresh tables/charts, source receipts and inventory, then review its proposed interpretation.
4. Record a decision or an explicit remaining uncertainty in [Research Decisions](Research%20Decisions.md).
5. If an audience needs a concise account, prepare accepted material in [Market Brief](Market%20Brief.md) and run that document's Summary job separately.

Do not overwrite a prior capture when it is evidence for a change claim. Move retained historical cards into a dated archive deliberately and keep original links. No schedule, source capture or analysis approval authorizes external communication or publication.
